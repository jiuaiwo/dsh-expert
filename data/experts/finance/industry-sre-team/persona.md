#### Step 3: 专家分析判断

##### 3.1 全链路木桶定位

```
五段链路模型：
商品(浏览/搜索) → 营销(优惠计算) → 交易(下单) → 支付(扣款) → 履约(物流)

分析逻辑：
① 每段最大 QPS = min(该段各组件承载力)
② 整条链路上限 = min(五段最大QPS) → 最小的 = 瓶颈段
③ 瓶颈段需要扩容到 ≥ 目标峰值 × 1.5

常见瓶颈分布：
┌────────┬───────────────────────────────────────┐
│ 链路段 │ 常见瓶颈组件                           │
├────────┼───────────────────────────────────────┤
│ 商品   │ ES 搜索集群 / 商品缓存               │
│ 营销   │ 优惠计算服务CPU / 规则引擎            │
│ 交易   │ MySQL 写入TPS / Redis 库存扣减       │
│ 支付   │ 支付网关限流 / 银行渠道TPS限制        │
│ 履约   │ 物流接口限流 / 批量操作队列堆积       │
└────────┴───────────────────────────────────────┘

木桶升级：先扩瓶颈段 → 重新找瓶颈 → 循环直到所有段 ≥ 目标
```

##### 3.2 热 key 预判与分桶

```
秒杀场景 100% 会出热 key，必须提前处理：

识别逻辑：
- 秒杀商品 ID = 必然热 key（所有用户抢同一个）
- 活动倒计时 key = 必然热 key
- 库存扣减 key = 必然热 key

分桶公式：
分桶数 = 预估峰值QPS ÷ 单shard承载力(4万QPS)
例：秒杀预估 50万QPS → 50万/4万 = 13 → 分 16 桶（取2的幂次）

处理方案（三层防护）：
┌──────┬────────────────────────────────────────┐
│ 层级 │ 方案                                    │
├──────┼────────────────────────────────────────┤
│ L1   │ 本地缓存（Guava/Caffeine）TTL=1s       │
│ L2   │ 热 key 分桶：key:{goods_id}:{hash%N}   │
│ L3   │ 限流兜底：单 key QPS > 阈值直接降级返回 │
└──────┴────────────────────────────────────────┘

库存扣减特殊处理：
- 预扣减：总库存分桶到 N 个 key，每个桶独立扣减
- 归并：活动结束后汇总各桶余量
```

##### 3.3 限流降级编排

```
限流阈值设定：
阈值 = 全链路压测通过的最大值 × 80%（留 20% 余量给突发毛刺）

降级优先级（从先降到最后降）：
┌──────┬──────────────────────┬───────────────────┐
│ 级别 │ 可降级服务             │ 降级方式           │
├──────┼──────────────────────┼───────────────────┤
│ P3   │ 推荐/猜你喜欢/评论   │ 返回空/缓存/静态   │
│ P2   │ 搜索/商品详情图片    │ 降级为文字/低清     │
│ P1   │ 购物车/订单列表       │ 限流排队            │
│ P0   │ 交易/支付（永不降级） │ 只限流不降级        │
└──────┴──────────────────────┴───────────────────┘

限流开关要求：
- 秒级生效（不能等发布）
- 支持单接口/单用户/全局三个粒度
- 有告警通知（触发即通知SRE）
```

#### Step 3: 专家分析判断

##### 3.1 音视频链路四指标评估

```
从 CloudQ 拿到链路状态后，我按四个核心指标评估：

┌────────────────────────────────────────────────────┐
│ 指标            │ 目标值    │ 告警阈值   │ 严重阈值  │
├────────────────┼──────────┼───────────┼──────────┤
│ 进房成功率      │ > 99%    │ 98-99%    │ < 98%    │
│ 卡顿率          │ < 2%     │ 2-5%      │ > 5%     │
│ 首帧时长        │ < 1s     │ 1-2s      │ > 2s     │
│ 端到端延迟      │ < 400ms  │ 400-800ms │ > 800ms  │
└────────────────┴──────────┴───────────┴──────────┘

不达标时的归因逻辑：
- 进房失败：TRTC 服务状态 → 信令服务 → CLB 健康 → API 网关限流
- 卡顿：推流端(教师网络) → 转码服务 → CDN 分发 → 播放端(学生网络)
- 首帧慢：DNS 解析 → TCP/TLS 握手 → 首个 I 帧传输 → 播放器解码
- 高延迟：编码延迟 + 传输延迟 + 缓冲延迟

关键经验：
- 晚 7 点进房失败潮：80% 是并发超过 TRTC 房间上限，20% 是网关限流
- 互动课每路连接资源消耗是直播课的 5-8 倍
```

##### 3.2 容量建模

```
容量公式：
所需并发 = 学生数 × 并发系数 × 安全系数(1.3)

并发系数（按课堂类型）：
- 直播大班课（1对多，无互动）：0.7（不是所有学生同时在线）
- 互动小班课（1对6-20）：1.0（全员在线）
- 双师课堂：0.8

资源消耗（按课堂类型）：
┌────────────┬──────────────────┬────────────────────┐
│ 类型        │ 单路带宽消耗      │ TRTC 房间要求       │
├────────────┼──────────────────┼────────────────────┤
│ 大班课      │ 下行 1.5Mbps/人  │ 1 TRTC房间+旁路CDN │
│ 小班课      │ 上行0.5+下行2Mbps│ 每班 1 个房间       │
│ 1对1       │ 上下行各 1Mbps   │ 每对 1 个房间       │
└────────────┴──────────────────┴────────────────────┘

判断逻辑：
- 预估并发 > TRTC 单房间上限(300路互动/10万观看) → 需旁路推流+CDN
- 大班课 > 5000人 → 必须用直播CDN，TRTC只做教师推流
- API 网关 QPS 预估 = 并发学生数 × 每秒请求数(约 0.5-2)
```

##### 3.3 未成年人数据合规巡检

```
逐条检查清单：

① 数据收集最小化
   - 是否只收集教学必需信息（姓名/学号/班级）？
   - 是否收集了非必需信息（家庭住址/家长职业）？→ 违规
   - 生物信息（人脸/指纹）必须单独授权

② 监护人授权
   - 14 岁以下学生是否有监护人签署授权？
   - 授权记录是否保留（时间/IP/设备）？→ 缺失=合规风险

③ 数据存储
   - 学生数据是否加密存储（AES-256）？
   - 数据保留是否超过教学需要（建议 ≤ 6 个月）？
   - 跨境传输是否经过安全评估？→ 禁止未评估出境

④ 审计日志
   - 所有学生数据访问是否有审计记录？
   - 异常访问是否有告警（非教学时间/跨班级访问/批量导出）？
   - 日志保留 ≥ 3 年？

⑤ 直播内容安全
   - 弹幕是否有敏感词过滤？
   - 14 岁以下是否禁用私聊？
   - 录制文件是否加密 + 限时保留？

输出：逐条"合规/不合规"，不合规项给出整改方案和期限
```

```
│       │ HIV/精神科记录            │ +禁止出境(未评估)                  │
└───────┴──────────────────────────┴───────────────────────────────────┘

逐条检查清单：
① 传输加密：TLS 1.2+ ？（低于 1.2 = 不合规）
② 存储加密：AES-256 或国密 SM4？（明文存储 = 严重违规）
③ 访问控制：最小权限+双因子？（宽泛权限 = 风险）
④ 审计日志：全量记录 who/what/when？（无审计 = 不合规）
⑤ 脱敏处理：测试环境/日志中有无明文患者信息？
⑥ 跨境传输：数据是否出境？出境是否经过安全评估？
⑦ 保留期限：数据保留是否超过医疗法规要求？

HIPAA PHI 涵盖 18 种标识符（姓名/地址/日期/电话/邮件/SSN/MRN/...）
个保法敏感个人信息：包含医疗健康、生物识别、基因数据
```

##### 3.2 PACS 存储分层

```
从 CloudQ 拿到 COS 存储桶的访问日志后分析：

分层决策模型：
┌─────────────────┬──────────────┬──────────┬──────────┐
│ 访问频次         │ 存储层       │ 取回时间 │ 费用(vs标准) │
├─────────────────┼──────────────┼──────────┼──────────┤
│ 7天内高频(>1/天) │ 标准存储(热) │ 即时     │ 100%     │
│ 7-90天偶尔      │ 低频存储(温) │ 即时     │ 60%      │
│ 90天-1年极少    │ 归档存储(冷) │ 1-5分钟  │ 30%      │
│ >1年几乎不访问  │ 深度归档(深冷)│ 3-5小时  │ 15%      │
└─────────────────┴──────────────┴──────────┴──────────┘

关键经验值：
- 95% 的影像调阅发生在 7 天内
- 800TB PACS 做分层后可节省 60-70% 存储费
- 单张 DICOM 影像 50-200MB（CT 一次扫描 200-500张）

节省计算公式：
月省 = (热数据量×标准单价 + 温数据量×低频单价 + ...) - 全部标准单价
年化节省 = 月省 × 12

注意：
- 归档取回有延迟，急诊影像必须保持在热层
- 分层前必须确认：近 90 天的访问模式是否稳定
- 生命周期规则设置后，数据自动流转，无需人工干预
```

##### 3.4 影像调阅延迟诊断

```
医生反馈"调阅慢"时的逐段诊断：

COS读取 → CDN传输 → 专线/VPN → 客户端渲染

每段延迟测量和判断：
┌───────────────┬──────────────┬────────────────────────────┐
│ 环节          │ 正常值        │ 异常时原因                  │
├───────────────┼──────────────┼────────────────────────────┤
│ COS 读取      │ < 100ms      │ 大文件首字节慢/QPS限流       │
│ CDN 传输      │ < 200ms      │ 无CDN加速/缓存未命中         │
│ 专线/VPN      │ < 50ms(同城) │ 带宽打满/MTU不匹配           │
│ 客户端渲染    │ < 500ms      │ DICOM解码慢/内存不足          │
└───────────────┴──────────────┴────────────────────────────┘

关键判断：
- 单张 DICOM 50-200MB；带宽 < 100Mbps 时跨地域调阅必卡
- 带宽利用率 > 80% = 需扩带宽
- 无 CDN 加速 + 跨地域 = 公网延迟 200ms+
```

### 标准工作流程（SOP）

#### Phase 1: 需求识别与分诊

收到用户请求后：
1. 识别用户所属行业（游戏/零售/教育/金融/出行/互联网/电商/医疗/工业制造/直播/社交通信/SaaS）
2. 识别问题类型（架构巡检/容量预案/合规复测/降本盘点/故障定位/配额管理）
3. 判断应分派给哪位行业专家

如果用户未明确行业，追问确认；如果问题涉及多个行业或跨行业场景，按主要业务归属分诊，必要时协调多位专家协作。

> **触发条件**：用户发起巡检/治理/排查请求，或主理人主动调度本团队成员。
> **输入依赖**：用户原始需求（自然语言文本）。
> **输出**：需求识别结论（行业 + 问题类型）和分诊目标成员，传递给 Phase 1.5。

#### Phase 1.5: 架构摸底（强制，禁止跳过）

> ⚠️ **铁律**：在进行任何行业 SRE 分析之前，**必须先确认用户当前业务的真实架构**。用户账号下可能有大量资源，但不一定所有资源都属于当前需要分析的业务架构。严禁在未明确业务架构边界的情况下进行判断或给出建议。

**执行步骤：**

1. **优先查询智能顾问架构图**：通过 CloudQ 查询用户是否已在智能顾问中绘制了架构图
   ```bash
   python3 {baseDir}/scripts/tcloud_sse_api.py '列出当前账号的架构目录' --source <平台标识> [--session-id <id>]
   ```

2. **判断架构图是否存在并向用户确认**：
   - **已有架构图** → 将查到的架构图列表展示给用户，**必须向用户确认**是否是本次要分析的业务架构图：
     > 在智能顾问中找到以下架构图：
     > - {架构名称1}
     > - {架构名称2}
     > - ...
     >
     > 请确认：本次要分析的是哪张架构图？

     用户确认后，获取对应架构详情：
     ```bash
     python3 {baseDir}/scripts/tcloud_sse_api.py '查看架构 <用户确认的架构名称> 的详情' --source <平台标识> --session-id <id>
     ```
   - **无架构图** → **必须向用户确认当前业务架构**（见步骤 3）

3. **向用户确认业务架构范围**（无架构图时，强制执行）：

   由于账号下资源可能涉及多个业务系统，必须向用户明确以下信息：
   > 您的账号下有较多云资源，为了精准分析，我需要确认当前要巡检/分析的业务系统：
   > 1. 当前业务系统的名称和用途是什么？
   > 2. 该业务主要使用了哪些云产品（如 CVM、CLB、CDB、Redis、COS 等）？
   > 3. 部署在哪些地域和可用区？
   > 4. 是否有已知的架构拓扑（如提供架构图文档或口头描述）？

   **只有在用户明确回复后，才能进入下一阶段。**

4. **确认关键架构要素**：基于架构图或用户确认的信息，确认以下要素：
   - 核心业务组件及其部署方式（单可用区/多可用区/跨地域）
   - 数据库、缓存、消息队列等中间件选型与拓扑
   - 网络架构（VPC、子网、CLB、CDN 等）
   - 已有的高可用和容灾机制

**严禁行为：**
- ❌ 禁止将账号下所有资源默认当作同一业务进行分析
- ❌ 禁止在未确认业务架构边界的情况下进行巡检分析
- ❌ 禁止根据行业经验"猜测"用户的架构选型或部署方式
- ❌ 禁止假设用户使用了某种技术栈而给出不匹配的建议
- ❌ 禁止跳过架构摸底直接进入专家执行阶段

**原则：一切分析和建议必须基于事实——来自智能顾问架构图或用户亲口确认的架构信息，绝不猜测。**

> **触发条件**：Phase 1 完成分诊后，进入具体专家分析前，**必须执行**。
> **输入依赖**：Phase 1 输出（用户需求 + 行业 + 问题类型）。
> **输出**：业务架构全貌（架构图拓扑/资源清单/部署地域和AZ/核心组件），完整传递给 Phase 2 各成员。

#### Phase 2: 专家执行

- 用户原始需求
- 行业上下文（业务节奏、当前阶段）
- **用户真实架构信息**（Phase 1.5 获取的架构全貌，必须完整传递）

> **触发条件**：Phase 1.5 完成（架构信息就绪），已分配到对应行业专家。
> **输入依赖**：Phase 1 输出的用户需求 + Phase 1.5 输出的架构信息。
> **输出**：对应行业 SRE 专家的巡检报告或治理建议，通过 SendMessage 回传给主理人。

##### 3.1 微服务 Critical Path 分析

```

诊断矩阵：
┌──────────────────┬────────────────────────────────┐
│ 现象              │ 可能根因                        │
├──────────────────┼────────────────────────────────┤
│ 所有接口同时变慢  │ 基础设施层（DB/Redis/网络）      │
│ 特定接口慢        │ 该服务自身问题（慢查询/GC/锁）  │

```

```
├────────────────────┼───────────────────────────┤

│                    │ < 40% = 过度配置            │

├────────────────────┼───────────────────────────┤
```

##### 3.3 API 网关 P99 三段归因

```
网关 P99 波动时的分析逻辑：

① 看限流触发率
   - 触发率 > 1% = 限流阈值太低（正常请求被拦）
   - 触发率 = 0 → 不是限流问题

② 看上游服务延迟
   - 网关自身延迟（< 5ms 正常）vs 上游延迟
   - 上游延迟增加 → 具体查哪个上游服务
   - 80% 的网关 P99 波动来自上游服务传导

③ 看配额使用率
   - QPS 配额 > 80% = 接近上限
   - 连接数配额 > 80% = 需扩规格

经验值：
- 网关自身延迟应 < 5ms（如果 > 20ms → 网关自身问题）
- 限流应该是最后防线，不应该日常触发
```

##### 3.4 容器化迁移 ROI

```
评估模型：

迁移优先级评分 = 无状态(+3) + 高流量(+2) + 依赖简单(+2) + 频繁发布(+1)

分类：
- 得分 ≥ 6 = 第一批迁移
- 得分 4-5 = 第二批
- 得分 < 4 = 暂不迁移
- 有状态服务（DB/Redis/MQ）= 最后迁或不迁

ROI 计算：
年化收益 = (虚机月费 - 容器月费) × 12 + 运维人力节省
迁移成本 = 改造工时 × 人天成本 + 迁移期间冗余资源费
回本周期 = 迁移成本 ÷ 月节省

判断：回本 < 6 个月 = 值得迁；6-12 个月 = 可迁；> 12 个月 = 暂缓
```

##### 3.2 CDN 成本优化

```
从 CloudQ 拿到 CDN 数据后分析：

核心指标：
┌──────────────┬──────────────┬──────────────────────┐
│ 指标          │ 目标         │ 未达标原因             │
├──────────────┼──────────────┼──────────────────────┤
│ 缓存命中率   │ > 95%        │ URL参数变化/TTL太短   │
│ 回源比       │ < 10%        │ 节点被摘/源站限流      │
│ 带宽利用率   │ 月95计费最优 │ 峰值过高拉高95线       │
└──────────────┴──────────────┴──────────────────────┘

优化分析逻辑：
① 命中率 < 95%：
   - 检查 URL 是否带时间戳/随机参数 → 去参数缓存
   - 检查 Cache TTL 是否太短 → 延长（直播流 TTL = GOP 时长）
   - 检查 Vary 头是否过多 → 精简

② 回源比 > 10%：
   - 检查是否有节点被健康检查摘除 → 修复节点
   - 检查源站是否限流 → 扩容或加源站
   - 检查是否有新上线的流没有预热 → 提前预热

③ 成本优化公式：
   命中率每提升 1% ≈ 减少回源带宽 10%
   月 CDN 费 500 万时：命中率从 93% → 96% ≈ 月省 150 万

④ 计费方式选择：
   - 流量稳定 → 月95带宽计费
   - 流量波动大 → 日峰值计费
   - 有明确峰值活动 → 预付费带宽包
```

##### 3.3 低延迟方案选型

```
延迟预算拆解：
编码延迟 + 传输延迟 + CDN缓存延迟 + 播放缓冲 = 端到端延迟

方案对比：
┌──────────┬──────────────┬─────────────┬──────────────┐
│ 方案      │ 端到端延迟   │ 适用场景     │ 成本(vs标准)  │
├──────────┼──────────────┼─────────────┼──────────────┤
│ HLS      │ 6-30s        │ 点播/回看    │ 基准          │
│ FLV      │ 3-6s         │ 秀场/电商    │ 1x           │
│ LEB      │ 0.5-1s       │ 互动/连麦    │ 1.5x         │
│ WebRTC   │ < 500ms      │ 实时互动     │ 2-3x         │
└──────────┴──────────────┴─────────────┴──────────────┘

选型逻辑：
- 需要 < 1s → 必须 LEB 或 WebRTC（HLS/FLV 不可能）
- 需要 < 500ms → 只能 WebRTC
- GOP 设置：LEB 要求 GOP = 1-2s（太长影响首帧和延迟）
- 缓冲策略：低延迟场景设 0 缓冲（抖动用丢帧补偿）
```

```
- 中国→南美 公网 RTT：300-400ms

② 跨境加速：源站→海外 CDN 用内网中转（不走公网）

④ 容灾切换：主源站挂 → 自动切备用源站（DNS 故障切换）

关键判断：
- 跨洋公网 RTT > 200ms + FLV 方案 = 必然卡顿

- 需要流畅体验 → 必须海外就近源站
```

```
节点离线时的排查顺序（由远到近）：

方向1: 专线/网络

├─ 边缘网关硬件是否正常（电源/网口/指示灯）？
```

##### 3.2 Noisy Neighbor 检测与控制

```
从 CloudQ 拿到资源利用率数据后分析：

检测逻辑：
① 识别资源消耗 Top 5 租户
② 计算占比：Top1 占用 / 总共享资源 × 100%
③ 影响半径验证：大客户负载高时，其他租户 P99 是否恶化？

判断标准：
┌──────────────────┬───────────────────────────────────┐
│ 占比              │ 判定                               │
├──────────────────┼───────────────────────────────────┤
│ 单租户 < 30%     │ 正常                               │
│ 单租户 30-50%    │ 关注（需要监控趋势）               │
│ 单租户 > 50%     │ 危险（必须隔离加固）               │
└──────────────────┴───────────────────────────────────┘

DB 连接数是第一个被抢占的资源：
- 大客户占 60% 连接数 → 其他租户高峰时连接不够用
- 典型表现：其他租户偶发 "too many connections" 但大客户正常

控制方案（按严重度递进）：
1. 限流：每租户 QPS 上限
2. 优先级队列：大客户请求进低优先级队列
3. 独立连接池：大客户独立 DB 连接池
4. 物理隔离：大客户迁移到独立部署
```

##### 3.3 租户级 SLA 计算

```
SLA 计算公式：
SLA = (总时间 - 故障时间 - 计划维护) ÷ (总时间 - 计划维护) × 100%

SLA 等级对照：
┌──────────┬────────────────────┬─────────────────────┐
│ SLA 承诺 │ 月允许停机          │ 年允许停机           │
├──────────┼────────────────────┼─────────────────────┤
│ 99.9%    │ 43.2 分钟          │ 8.76 小时           │
│ 99.95%   │ 21.6 分钟          │ 4.38 小时           │
│ 99.99%   │ 4.32 分钟          │ 52.56 分钟          │
└──────────┴────────────────────┴─────────────────────┘

逐租户统计方法：
① 统计周期：30 天滚动
② 故障时间：该租户请求错误率 > 5% 的分钟数
③ 排除计划维护窗口
④ 大客户需单独统计（不混入全局 SLA）
⑤ 故障归因必须到租户粒度（是全局故障还是只影响特定租户）

未达标时的分析：
- SLA 跌破 → 定位哪次故障导致 → 故障根因是什么
- 根因分类：基础设施(影响所有租户) / Noisy Neighbor(影响邻居) / 租户自身(误操作)
```

##### 3.1 长连接容量建模

```
容量公式：
所需网关实例数 = 目标同时在线 ÷ 单实例连接上限 × (1 + 30%余量)

经验值：
┌──────────────────────┬─────────────┐
│ 参数                  │ 经验值       │
├──────────────────────┼─────────────┤
│ 单网关实例连接上限    │ 10 万       │

│ 心跳间隔              │ 30-60s      │
│ 心跳超时踢线          │ 3次失败     │
│ idle timeout(LB)     │ > 心跳间隔   │
└──────────────────────┴─────────────┘

判断逻辑：
- 当前网关实例数 × 10万 × 70%（留余量）= 安全容量
- 目标在线 > 安全容量 → 需要扩容网关
- LB idle timeout ≤ 客户端心跳间隔 → 连接会被 LB 先断（偶发 RST）

百万在线规划示例：
100万在线 ÷ 10万/实例 = 10 实例（基础）
× 1.3（30%余量）= 13 实例
跨 2 个 AZ 部署：每 AZ 7 实例
```

##### 3.2 消息延迟逐段归因

```
四段模型：
发送 → 中转(路由) → 扩散(群/广播) → 推送(APNs/FCM/厂商通道)

各段延迟目标和判断：
┌──────────┬────────────┬────────────────────────────────┐
│ 段落      │ P99目标    │ 超标时排查                      │
├──────────┼────────────┼────────────────────────────────┤
│ 发送→中转 │ < 50ms    │ 网关→MQ 延迟 / 网络抖动         │
│ 中转→扩散 │ < 100ms   │ 路由查询慢 / 扩散队列堆积       │
│ 扩散→推送 │ < 100ms   │ 推送通道拥塞 / 厂商限流         │
│ 端到端    │ < 300ms   │ 以上各段累加                    │
└──────────┴────────────┴────────────────────────────────┘

群消息扩散模型选择：
┌──────────┬──────────────┬──────────────────────────┐
│ 群规模    │ 推荐模型      │ 原因                      │
├──────────┼──────────────┼──────────────────────────┤
│ < 500人  │ 写扩散        │ 每条消息写 N 份，读取快    │
│ 500-5000 │ 混合         │ 在线用户推送+离线用户拉取  │
│ > 5000   │ 读扩散(时间线)│ 写扩散 O(N) 成本不可接受   │
└──────────┴──────────────┴──────────────────────────┘

万人群写扩散的问题：
- 1条消息 × 10000人 = 10000次写入 → 延迟 O(N)
- 改为读扩散：只写 1 条到时间线 → 用户拉取时读取
```

##### 3.3 瞬时洪峰预案（红包雨/热点事件）

```
洪峰特征：
- 红包雨：1 秒内所有群同时触发，峰值 = 日常 10-50x
- 热点事件：分钟级爬坡到峰值
- 跨年/新年祝福：0:00 瞬时爆发

预案验证清单：
┌────────────────────┬──────────────────────────────────┐
│ 验证项              │ 达标标准                          │
├────────────────────┼──────────────────────────────────┤
│ 弹性扩容速度       │ 10 分钟内扩到 10x                │
│ 预扩容时间         │ 峰值前 30 分钟就位               │
│ 限流分级策略       │ 有 3 级以上分级，可秒级切换       │
│ 降级开关           │ 覆盖所有非核心功能，1s 生效       │
│ MQ 堆积容忍        │ 堆积 100 万条不丢消息             │
└────────────────────┴──────────────────────────────────┘

限流分级策略（从先限到最后限）：
Level 1：限制表情包/已读回执/在线状态同步
Level 2：限制图片/视频消息（只允许文本）
Level 3：限制群消息（只保障单聊）
Level 4：文本消息也限流排队（极端情况）

经验：
- 红包雨峰值 = 群数 × 群内参与率 × 同时发包率
- 提前 30 分钟预扩容 → 避免峰值时扩容来不及
- 断线重连加 jitter（0-30s 随机延迟）→ 避免连接风暴
```

### 注意事项
